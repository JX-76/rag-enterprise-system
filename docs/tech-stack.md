# 技术栈选型说明

> 实战项目的技术选型，基于实际需求和长期维护成本

---

## 选型原则

1. **够用就好**：不追新，选成熟稳定的
2. **维护成本**：优先选团队熟悉的技术
3. **渐进扩展**：小团队起步，随规模升级

---

## 逐层说明

### 1. FastAPI

**实际用途**：
- 异步支持，适合IO密集型场景（LLM调用、向量检索）
- 自动生成API文档，前后端联调省时间
- 类型检查，减少低级bug

**不选Flask/Django的原因**：
- Flask异步支持弱，高并发需gevent/eventlet
- Django太重，不需要admin后台

---

### 2. LangChain

**实际用途**：
- 快速接入不同LLM（OpenAI/通义千问切换方便）
- 向量库集成成熟，不用自己写客户端
- 中间件机制（回调、重试）开箱即用

**使用策略**：
- 用LangChain快速搭建原型
- 核心模块（分块、检索）手写替换
- 两者结合，不是非此即彼

---

### 3. 向量数据库

**当前：ChromaDB**
- 本地文件存储，零运维成本
- 足够支撑十万级文档
- 开发阶段省时间

**未来：Milvus**
- 文档量超百万时迁移
- 分布式、多租户支持更好
- 有完整的Python SDK

**不选Pinecone的原因**：
- 托管服务，数据在第三方
- 有vendor lock-in风险
- 调用成本随量上涨

---

### 4. PostgreSQL + Redis

**PostgreSQL**：
- 关系型数据存metadata、用户信息
- pgvector扩展可做简单向量检索（小量数据）
- 一个数据库管所有，省维护成本

**Redis**：
- 缓存热点查询结果
- Celery消息队列后端
- 缓存向量数据库查询（减少重复计算）

**不选MongoDB的原因**：
- PostgreSQL JSONB也能存半结构化数据
- 减少技术栈复杂度，维护省事

---

### 5. Celery

**实际用途**：
- 文档处理（PDF解析、向量化）耗时，异步化避免阻塞
- 失败重试机制（网络抖动导致LLM调用失败）
- 定时任务（清理过期缓存、统计报告）

**不选Kafka/RabbitMQ的原因**：
- 单机/小集群Celery够用
- Kafka运维成本高，需要专人维护
- RabbitMQ配置复杂，Celery+Redis更简单

---

### 6. Prometheus + Grafana

**实际用途**：
- 监控API响应时间、错误率
- 监控LLM调用成本和延迟
- 监控向量检索性能

**替代方案**：
- 云服务监控（CloudWatch/云监控）：如果用云托管可以省掉
- 当前自己部署，用开源方案成本低

---

## 明确不用的技术

| 技术 | 不用原因 |
|------|----------|
| LlamaIndex | 与LangChain功能重叠，维护两套成本高 |
| Elasticsearch | 太重，Whoosh轻量够用 |
| Kafka | 单机Celery够用 |
| MongoDB | PostgreSQL JSONB够用 |
| Airflow/Prefect | 当前场景不需要复杂工作流 |

## 部署方案

### 本地开发
```bash
docker-compose up -d  # ChromaDB + Redis
python -m src.api.main
```

### 小团队生产（当前）
```bash
# 单机部署
docker-compose -f docker-compose.yml up -d
```

### 规模扩大后（未来）
```bash
# Kubernetes
kubectl apply -f k8s/
```

## 扩展路径

```
当前（单机）
  ↓ 文档量增长
PostgreSQL → 读写分离
  ↓ 查询量增长
Redis Cluster + 多级缓存
  ↓ 向量规模增长
ChromaDB → Milvus
  ↓ 团队规模增长
单体 → 微服务拆分
```

按实际需求渐进升级，不提前过度设计。
