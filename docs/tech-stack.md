# 技术栈选型说明

> 精选一套**实用、主流、面试友好**的技术方案

---

## 核心选型原则

1. **单一职责**：每个领域只选一个最优解
2. **生态成熟**：社区活跃，文档完善
3. **面试友好**：技术选型能讲清楚"为什么"

## 逐层选型理由

### 1. API层：FastAPI

**为什么选它**：
- 异步原生支持（async/await）
- 自动生成OpenAPI文档
- 类型安全（Pydantic）
- 性能接近Go/Node.js

**面试话术**：
> "相比Flask/Django，FastAPI的异步性能更适合高并发LLM应用，类型注解也减少了运行时错误。"

### 2. LLM框架：LangChain

**为什么选它**：
- 生态最成熟，社区最大
- 与各类向量库集成完善
- 面试问得最多

**为什么不选LlamaIndex**：
- 功能重叠，二选一即可
- LangChain更通用，LlamaIndex更偏检索

**面试话术**：
> "LangChain适合快速搭建原型，但生产环境需要手写核心模块（如熔断器、分块策略）来精细控制。"

### 3. 向量数据库

| 场景 | 选择 | 理由 |
|------|------|------|
| 本地开发 | **ChromaDB** | 轻量、无需部署 |
| 生产环境 | **Milvus** | 企业级、分布式、性能优秀 |
| 关系+向量 | **pgvector** | 减少技术栈复杂度 |

**面试话术**：
> "ChromaDB适合本地快速验证，Milvus适合生产大规模向量检索，pgvector适合不想维护多套数据库的场景。"

### 4. 数据存储：PostgreSQL + Redis

**为什么**：
- PostgreSQL：最成熟的开源关系型数据库
- pgvector扩展：一个数据库搞定关系和向量
- Redis：缓存 + 消息队列（Celery）一物两用

**为什么不选MongoDB**：
- PostgreSQL JSONB也能存半结构化数据
- 减少技术栈复杂度

### 5. 任务队列：Celery

**为什么选它**：
- Python生态最成熟
- 与Redis集成简单
- 支持定时任务、重试机制

**为什么不选Kafka/RabbitMQ**：
- 单机/小集群Celery够用
- Kafka太重，学习成本高

**面试话术**：
> "文档处理是IO密集型任务，用Celery异步化避免阻塞主服务，支持失败重试和任务追踪。"

### 6. 监控：Prometheus + Grafana

**为什么**：云原生监控标准，面试必问。

## 明确不用的技术

| 技术 | 不用原因 |
|------|----------|
| LlamaIndex | 与LangChain功能重叠，二选一 |
| Elasticsearch | 太重，Whoosh轻量够用 |
| Kafka | 单机Celery够用，Kafka运维成本高 |
| Airflow/Prefect | 简单场景不需要工作流引擎 |
| Istio | 服务少的时候用不上 |

## 部署方案

### 本地开发
```bash
docker-compose up -d  # 只启动ChromaDB + Redis
python -m src.api.main  # 本地启动API
```

### 生产环境
```bash
# 方案A：简单部署
docker-compose -f docker-compose.prod.yml up -d

# 方案B：Kubernetes（流量大时）
kubectl apply -f k8s/
```

## 面试回答模板

**Q：为什么不用LlamaIndex？**
> "调研过，LlamaIndex在检索场景有优势，但LangChain生态更成熟、社区更大。考虑到团队熟悉度和招聘友好度，选了LangChain。两者核心思想类似，切换成本不高。"

**Q：向量数据库为什么选Milvus？**
> "对比过几个方案：ChromaDB轻量但功能简单，Pinecone是托管服务有 vendor lock-in，Weaviate学习成本高。Milvus在企业级场景（分布式、多租户、混合检索）表现最好，而且有中文文档支持。"

**Q：为什么手写熔断器，不用现成的？**
> "看过resilience4j和pybreaker，但我们的场景需要自定义恢复策略（比如LLM服务降级到本地模型），手写可以精细控制状态转换逻辑，也是学习微服务稳定性的好机会。"
